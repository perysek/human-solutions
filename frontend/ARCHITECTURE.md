# React vs. vanilla HTML/CSS/JS — and how this frontend is built

This project exists twice in this repo: the reference implementation
(`templates/`, `static/js/`, Flask/Jinja2) and the rebuild (`frontend/`,
React/TypeScript/Vite). That makes it an unusually concrete place to explain
*why* the two approaches differ, not just *that* they do — every claim below
points at a real file on both sides.

## 1. The core shift: imperative DOM mutation vs. declarative rendering

**Vanilla (reference project).** The server renders complete HTML
(`templates/components/sidebar.html`), the browser loads it once, and a
plain `<script>` block then reaches into that HTML and mutates it by hand in
response to events:

```js
// templates/components/sidebar.html — accordion open/close
items.style.maxHeight = items.scrollHeight + 'px';
btn.setAttribute('aria-expanded', 'true');
```

The *state* — "which section is open" — doesn't exist anywhere as data. It's
implicit in the DOM: to know if a section is open, other code has to query
`items.style.maxHeight !== '0px'`. Every place that cares about that state
has to independently read and stay in sync with the DOM itself.

**React (`frontend/`).** State is an explicit JS value, and the DOM is
treated as an output you never touch directly — you describe what should be
on screen *for the current state*, and React computes the minimal set of
real-DOM changes to get there:

```tsx
// frontend/src/components/layout/Sidebar.tsx
const [openSectionId, setOpenSectionId] = useState<string | null>(activeSectionId);
// ...
<SidebarSection open={openSectionId === section.id} onToggle={...} />
```

`openSectionId` is a real, inspectable value. "Which section is open" has
exactly one source of truth. The `max-height` pixel calculation still has to
happen imperatively somewhere (CSS transitions need a real number, not
`auto`) — but in `SidebarSection.tsx` it lives inside a `useEffect` that
*reacts to* the `open` prop changing, rather than being the mechanism that
drives everything else.

## 2. The unit of reuse: one file vs. three languages kept in sync by hand

**Vanilla.** A reusable "component" is actually three separate artifacts
that have to be edited together: a Jinja macro for markup
(`templates/macros/sidebar_macros.html`), a CSS class for style
(`static/css/input.css`'s `.sidebar-link--active`), and — for anything with
behavior — a shared global JS file (`static/js/modals.js`). The component
docs in `gui-components/` exist largely *because* keeping these three in
sync isn't automatic; `confirm-modal.md` explicitly calls out that its
`<style>` block must stay inline in the same file as its markup+script,
specifically to stop that drift.

**React.** Markup, local state, and behavior live in one file:

```tsx
// frontend/src/lib/feedback/ConfirmProvider.tsx — the whole confirm dialog
export function ConfirmProvider({ children }) {
  const [isOpen, setIsOpen] = useState(false);
  // ...
  return (/* JSX markup for the dialog */)
}
```

Styling still lives in a separate CSS file here (`frontend/src/styles/
components.css`, ported class-for-class from `input.css` to keep the design
identical) — but the *structure and behavior* of a component, which is what
actually changes over a component's lifetime, is unified. A Jinja macro call
(`sidebar_link(url, label, icon_path, is_active)`) and a React element
(`<SidebarLink to={...} label={...} />`) look similar at the call site, but
the macro is pure templating — it has no memory, no lifecycle, nothing runs
when it "mounts" or "unmounts". A React component can hold its own state
(`ThemeSwitcher.tsx` tracks its popover's open/closed state internally) and
run code at defined moments (`useEffect` on mount, on prop change, on
unmount) — capabilities a template language doesn't have.

## 3. Data flow: full-page round-trips vs. client-side fetch + re-render

**Vanilla.** Every navigation is a full HTTP request: the server queries
Postgres, renders complete HTML server-side, and the browser replaces the
entire page. `templates/users/list.html` (never fully built in this repo,
but structurally what the reference implies) would be regenerated by Flask
on every visit. In-page interactivity — search filtering a table, sorting a
column — is bolted on afterward with page-specific vanilla JS reading and
rewriting the already-rendered DOM.

**React (this app).** The server sends `frontend/index.html` exactly once.
After that, `frontend/src/router.tsx` (React Router) swaps which components
are mounted based on the URL — no page reload. Data arrives via a typed
`fetch()` wrapper (`frontend/src/lib/api/client.ts`) hitting the same JSON
endpoints the Flask backend exposes (`/system/users/api`, `/employees/api`,
...), lands in component state via the `useApiData` hook
(`frontend/src/lib/api/useApiData.ts`), and the UI re-renders automatically
— nobody manually writes "now update the DOM" code anywhere in this app.

## 4. How `frontend/` is organized, and why

```
frontend/src/
  styles/       Design tokens + component CSS. No JS/TS — pure CSS, ported
                verbatim from the reference input.css.
  lib/          Framework-agnostic logic: auth session state, typed API
                clients, the icon dictionary, toast/confirm providers.
                Nothing here renders page-specific UI or imports from pages/.
  components/   Reusable UI building blocks (Button, PageHeader, Sidebar,
                SortableTh, ...). Generic — a component here doesn't know
                which page is using it.
  pages/        One folder per resource (users/, roles/, employees/),
                composing components/ + lib/ into actual screens.
  router.tsx    Wires URLs to pages, applies permission guards.
  App.tsx       Wraps everything in the context providers (auth, toast,
                confirm) that lib/ and components/ depend on.
  main.tsx      The actual entry point — see §5.
```

The dependency direction only ever points one way:
**pages → components → lib**. `lib/` never imports from `components/` or
`pages/`; `components/` never imports from `pages/`. Nothing enforces this
mechanically (no lint rule currently checks it) — it's a convention, kept
because violating it is what turns a component tree into a tangle where
changing one page's code breaks another's.

`@/` as an import prefix (`import { Button } from '@/components/ui/Button'`)
is a path alias configured in two places that must agree —
`vite.config.ts`'s `resolve.alias` (so the bundler resolves it) and
`tsconfig.json`'s `compilerOptions.paths` (so the type-checker and editor
tooling resolve it identically). It exists purely to avoid `../../../../`
relative-path chains as files move around.

## 5. From source files to what the browser actually loads

**Dev mode (`npm run dev`).** Vite does *not* bundle the app up front.
It starts a dev server that serves your source files as native browser ES
modules, transforming each one (TSX → JS, CSS → an injectable JS module)
**on demand**, the first time the browser actually requests it. That's why
Vite's dev server starts in well under a second regardless of project size
— compare to a bundler-based dev server, which has to build the whole
dependency graph before it can serve the first byte. When you save a file,
Vite pushes just that module's new code to the browser over a WebSocket, and
React's Fast Refresh patches the running component tree in place —
preserving component state — instead of reloading the page. (Watch this
happen in `npm run dev`'s terminal output: `hmr update /src/pages/
users/UsersListPage.tsx`.)

**Production build (`npm run build`, i.e. `tsc -b && vite build`).**

1. `tsc -b` type-checks the *entire* project and fails the build on any
   type error. It emits no runtime code that ships to the browser — Vite
   uses esbuild to strip TypeScript types during the actual build, which is
   why `tsc` here is purely a correctness gate, not part of the output
   pipeline.
2. `vite build` (Rollup under the hood) starts at `index.html`, follows
   every `import` starting from `src/main.tsx`, and bundles the whole
   reachable graph into a small number of hashed, minified files:
   `dist/assets/index-[hash].js`, `dist/assets/index-[hash].css`. Unused
   code is tree-shaken out; the content hash in each filename means a
   browser (or CDN) can cache these files forever, since any code change
   produces a new filename.

**What the browser does with it.** `dist/index.html` contains one line that
matters: `<script type="module" src="/assets/index-[hash].js">`. A static
file server hands that HTML to the browser, which downloads and executes the
bundle. The very first thing that bundle does is:

```tsx
// frontend/src/main.tsx
ReactDOM.createRoot(document.getElementById('root')!).render(<App />);
```

That call is the exact moment React takes over the (until then empty)
`<div id="root">` from `index.html` and starts turning the component tree
into real DOM nodes. Every navigation, every data fetch, every re-render
from that point on happens inside that one loaded bundle — the browser makes
no further full-page requests to the server, only background `fetch()`
calls for JSON data.

**Contrast.** The reference project has no comparable build step for its
own JS: `static/js/*.js` files are loaded as classic `<script src="...">`
tags in `base.html`, in a specific hand-maintained order (`utils.js` before
`api.js` before `notifications.js`, ...) because they're not ES modules —
they attach to `window` as globals (`Notifications.show`, `Modals.confirm`)
rather than `export`ing anything, since nothing bundles or resolves imports
between them. Tailwind's CSS is the one piece that *does* have a build step
on that side too (`input.css` → `output.css` via the Tailwind CLI) — which
is exactly why `GUI-GOLDEN-BOOK.md` calls out `output.css` being gitignored
as a deployment trap: forget the build step, and the server ships unstyled
HTML.

## 6. Side-by-side summary

| | Vanilla (reference) | React (`frontend/`) |
|---|---|---|
| State lives in | The DOM itself (queried back via `style`/`dataset`/`classList`) | Explicit JS values (`useState`), DOM is a derived output |
| Reusable unit | 3 files kept in sync by convention: Jinja macro + CSS class + global JS | 1 component file (markup + state + behavior); CSS still separate |
| Page navigation | Full HTTP round-trip, server re-renders whole page | Client-side route swap (React Router), no reload |
| Data fetching | Baked into the server-rendered HTML at request time | `fetch()` after mount, UI re-renders when state updates |
| JS module system | None — classic scripts, globals (`window.Notifications`) | ES modules, `import`/`export`, bundler resolves the graph |
| Styling delivery | Tailwind CLI build (`input.css` → `output.css`), gitignored output | Same idea, via Vite's built-in CSS pipeline |
| Dev feedback loop | Edit template/JS → full page reload | Edit component → Hot Module Replacement, state preserved |
| Production output | Server renders HTML per-request, forever | One-time static bundle (`dist/`), hashed + cached |
